# 旅行规划平台 —— 技术方案（第二版）

> 版本：v2.0 ｜ 日期：2026-09-05 ｜ 状态：待评审
>
> 本文档在 v1.0 基础上演进，核心变更：高德地图接入方式从「托管 SSE MCP 端点」切换为「本地 stdio MCP 子进程（官方 `@amap/amap-maps-mcp-server`）」，并新增**路线规划**与**坐标回填修复**。文中标出的实现细节均与当前代码一致。

## 版本变更摘要（v1.0 → v2.0）

| # | 变更点 | v1.0 | v2.0 |
|---|--------|------|------|
| 1 | 地图接入方式 | 托管 SSE MCP 端点（长连接易被断开） | **本地 stdio MCP 子进程**（npx 拉起官方服务器，连接稳定） |
| 2 | 工具范围 | 搜索 + 天气 | 搜索 + 天气 + **路线规划**（`direction_*`） |
| 3 | 坐标回填 | 缺失（`text_search` 无坐标，地图无标记） | `search_detail` 补齐 + 名称回填 + `maps_geo` 兜底 |
| 4 | Agent 图结构 | 2 节点（gather → plan） | **3 节点（gather → plan → enrich）** |
| 5 | 数据结构 | 无路线字段 | 新增 `RouteSegment`，`DayPlan.routes` 承载每日路线 |
| 6 | 前端 | 仅景点标记 | 新增「交通路线」渲染块 + 地图每日折线 |
| 7 | 部署 | 后端纯 Python 镜像 | 后端镜像**内置 Node.js**，全局预装 MCP 服务器 |

## 1. 项目概述

### 1.1 背景与目标

构建一个 **AI 驱动的旅行规划平台**：用户输入目的地、日期、偏好等信息后，系统通过多智能体协作自动生成包含景点、酒店、餐饮、天气、**交通路线**、预算的完整行程；支持用户账户管理、历史行程保存与行程分享。

与参考项目 `Trip` 的关系：

| 维度 | 参考项目 `Trip` | 本项目（v2.0） |
|------|----------------|----------------|
| Agent 框架 | HelloAgents（SimpleAgent） | **LangChain + LangGraph** |
| 地图服务 | 高德 MCP（`amap-mcp-server`） | 高德官方 MCP（本地 `@amap/amap-maps-mcp-server`，stdio） |
| 数据持久化 | 无（仅 sessionStorage） | **PostgreSQL / SQLite + 用户历史行程** |
| 用户系统 | 无 | **注册/登录（JWT）+ 行程归属** |
| 分享协作 | 无 | **分享链接（只读查看）** |
| 结构化输出 | 手写 `[TOOL_CALL:...]` + 字符串解析 JSON | **LLM JSON 模式 + `TripPlan` 校验** |
| 天气 | 单次查询 | 按行程日期范围取预报 |
| 路线规划 | 无 | **每日相邻景点 `direction_*` 路线** |
| 坐标回填 | 无 | **`search_detail` + `maps_geo` 双重补齐** |
| 部署 | 本地 dev | **Docker + Nginx + PostgreSQL**（后端含 Node） |

### 1.2 核心功能清单（已实现）

- **行程生成**：单城市多日行程，含景点、三餐、酒店、天气、交通路线、预算
- **用户账户**：注册 / 登录 / 个人信息
- **历史行程**：保存、查看、删除自己的行程
- **行程分享**：生成分享链接，他人只读查看（无需登录）
- **地图可视化**：景点标记 + 每日路线折线（高德 JS API 2.0）
- **景点图片**：Unsplash 关键词搜图（可选，未配置 key 时静默降级）

> 预留未实现（后续版本）：行程导出（图片/PDF）、行程编辑、分享「复制到我的账户」。

### 1.3 非功能需求

| 类别 | 要求 |
|------|------|
| 性能 | 行程生成 ≤ 2 分钟（实测约 35s）；非 LLM 接口 P95 < 500ms |
| 安全 | 密码 bcrypt 哈希；JWT 鉴权；分享 token 随机不可枚举；CORS 白名单；ORM 防注入 |
| 可靠性 | 单个 MCP 工具调用失败降级不阻断整体；MCP 子进程异常可重建会话；结构化输出失败可兜底 |
| 可扩展 | 服务层解耦，LLM / 地图 / 图片供应商可替换 |
| 可观测 | 结构化日志（loguru）、健康检查端点 `/health` |

### 4.2 Agent 编排层（LangGraph）

**State 定义**（`state.py`）：

```python
from typing import Any, Dict, List, Optional, TypedDict

class PlannerState(TypedDict, total=False):
    # 输入
    city: str
    start_date: str
    end_date: str
    travel_days: int
    transportation: str
    accommodation: str
    preferences: List[str]
    free_text: str
    # 取数产出
    attractions: List[Dict[str, Any]]
    weather: List[Dict[str, Any]]
    hotels: List[Dict[str, Any]]
    # 计划产出
    plan: Optional[Dict[str, Any]]
```

**图结构**：三段式串行——取数 → 规划 → 后处理。

```
START → gather（确定性调用高德 MCP 工具取数）
      → plan  （LLM JSON 模式生成计划）
      → enrich（坐标回填 + 每日路线规划）
      → END
```

**节点说明**：

| 节点 | 实现方式 | 说明 |
|------|---------|------|
| `gather` | 确定性调用 MCP 工具（无 LLM） | `text_search` 搜景点/酒店 → `search_detail` 补坐标/评分 → `weather` 取天气 |
| `plan` | LLM + JSON 模式（`response_format=json_object`） | 综合数据生成完整 TripPlan（DeepSeek 对深层嵌套 schema 的 function calling 不稳定，故用 JSON 模式） |
| `enrich` | 确定性（无 LLM） | ① 按名称把真实坐标回填到景点/酒店（匹配不到则 `maps_geo` 兜底）；② 对每天相邻景点调用 `direction_*` 生成路线 |

**关键实现要点**：

- 工具由 `langchain-mcp-adapters` 通过 stdio 拉起官方 MCP 服务器获得，代码直接 `tool.ainvoke(args)` 确定性调用，不依赖 LLM 的 ReAct 循环（避免漏调天气/酒店/路线）。
- `plan` 节点的目标 JSON Schema 会**剔除 `routes` 字段**，路线由 `enrich` 节点确定性补充，避免 LLM 乱填。
- 结构化输出：`TripPlan.model_validate()` 校验，失败时 `_parse_plan_json` 兜底截取 JSON。
- MCP 工具单例懒加载，子进程生命周期与应用一致，关停时 `close_amap_mcp()` 释放。

**降级策略**：`gather`/`enrich` 中单个工具调用失败（某 POI 详情、某段路线）捕获异常继续，不影响整体；MCP 子进程异常时重建会话重试一次。

### 4.3 工具层（高德官方 MCP 服务器）

通过 `langchain-mcp-adapters` 以 stdio 传输方式拉起高德官方 MCP 服务器
（`@amap/amap-maps-mcp-server`，npx 子进程，key 经环境变量 `AMAP_MAPS_API_KEY` 注入），
直接复用官方提供的 12 个地图工具，本流程用到其中 **7 个**：

| MCP 工具 | 入参 | 用途 |
|---------|------|------|
| `maps_text_search` | `keywords, city, types` | 关键词搜 POI（只返回 id/name/address，不含坐标） |
| `maps_search_detail` | `id` | POI 详情，补齐 location/type/rating/图片 |
| `maps_weather` | `city` | 天气预报（一步到位，无需先查 adcode） |
| `maps_geo` | `address, city` | 地理编码，坐标回填兜底 |
| `maps_direction_walking` | `origin, destination` | 步行路线（`lng,lat`） |
| `maps_direction_driving` | `origin, destination` | 驾车路线 |
| `maps_direction_transit_integrated` | `origin, destination, city, cityd` | 公交/地铁综合路线 |

**坐标补齐**：`maps_text_search` 不返回坐标，`gather` 节点对每个 POI 再调 `maps_search_detail`
获取真实坐标；`enrich` 节点回填时匹配不到再用 `maps_geo(address)` 兜底。

**路线**：方向工具返回 `distance`(米) + `duration`(秒) + `steps`，但不含 polyline 轨迹，
前端地图用「景点直线连线」呈现每日路线，文字展示里程/耗时/步骤。短途公交结果缺失 `duration`
时做两级兜底（累计步行段时长 → 按 1.2 m/s 步行速度估算）。

### 4.4 数据模型（Pydantic Schemas）

行程核心模型（`schemas/trip.py`）：

```python
class Location(BaseModel):
    name: str
    address: str = ""
    longitude: float = 0.0
    latitude: float = 0.0

class Attraction(BaseModel):
    name: str
    description: str = ""
    address: str = ""
    location: Optional[Location] = None
    suggested_duration: str = ""
    image_url: str = ""

class RouteSegment(BaseModel):
    """每日行程中相邻景点之间的交通路线（enrich 节点确定性生成）"""
    from_name: str = ""
    to_name: str = ""
    mode: str = ""              # walking / driving / transit
    distance_m: int = 0
    duration_s: int = 0
    summary: str = ""
    steps: List[str] = Field(default_factory=list)

class DayPlan(BaseModel):
    day: int
    date: str = ""
    title: str = ""
    attractions: List[Attraction] = Field(default_factory=list)
    meals: List[Meal] = Field(default_factory=list)
    hotel: Optional[Hotel] = None
    transportation_tips: str = ""
    routes: List[RouteSegment] = Field(default_factory=list)   # ← v2 新增
    notes: str = ""

class TripPlan(BaseModel):
    city: str
    start_date: str
    end_date: str
    travel_days: int
    overview: str = ""
    days: List[DayPlan] = Field(default_factory=list)
    weather: List[WeatherInfo] = Field(default_factory=list)
    budget: Optional[Budget] = None
    tips: List[str] = Field(default_factory=list)
```

class RegisterRequest(BaseModel):

## 5. 数据库设计

> 实际采用 **同步 SQLAlchemy**，`DATABASE_URL` 默认 `sqlite:///./trip.db`，生产切 PostgreSQL。启动时 `Base.metadata.create_all` 建表。

**users**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | PK autoincrement | |
| email | varchar unique | 登录邮箱 |
| username | varchar unique | 昵称 |
| password_hash | varchar | bcrypt 哈希 |
| created_at / updated_at | timestamptz | |

**trips**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | PK autoincrement | |
| user_id | FK → users.id（索引） | 归属用户 |
| city / start_date / end_date | varchar | 行程输入 |
| travel_days | int | 默认 1 |
| transportation / accommodation | varchar | 默认「公共交通 / 经济型酒店」 |
| preferences | jsonb | 偏好标签数组 |
| free_text | text | 额外要求 |
| plan | jsonb | **完整生成结果（结构化 JSON，含 routes）** |
| status | varchar | completed / failed |
| created_at | timestamptz | |

> 设计取舍：行程完整结果存 `jsonb`（而非拆分景点/餐饮/酒店多表）。理由：行程是 LLM 生成的非规范化对象，拆分表在小规模场景收益低、维护成本高。

**share_links**

| 字段 | 类型 | 说明 |
|------|------|------|
| id | PK autoincrement | |
| trip_id | FK → trips.id | 被分享的行程 |
| token | varchar unique | 随机 256-bit（`secrets.token_urlsafe(32)`） |
| created_by | FK → users.id | |
| expires_at | timestamptz nullable | 过期时间 |
| created_at | timestamptz | |

**索引**：`users(email)`、`users(username)`、`trips(user_id)`、`share_links(token)`（均唯一/索引）。

## 7. 关键流程

### 7.1 行程生成流程

```
用户填写表单 → POST /api/trips/generate
  → LangGraph 图执行（串行）：
       gather  : text_search 搜景点/酒店 → search_detail 补坐标 → weather 取天气
       plan    : LLM JSON 模式生成 TripPlan（无 routes）
       enrich  : 坐标回填（名称匹配 + geo 兜底）→ 相邻景点 direction_* 生成路线
  → TripPlan 校验 → 返回 { success, message, data }
  → 前端跳转 /result 展示（地图标记 + 每日折线 + 交通路线）
  → 用户点「保存」→ POST /api/trips 持久化
```

### 7.2 分享流程

```
分享: 用户点「分享」→ POST /api/share/trips/{trip_id} → 生成 token → 返回 /share/{token}
访问: 他人打开 /s/{token} → GET /api/share/{token} → 只读渲染（校验过期）
```

### 7.3 注册/登录流程

```
注册: POST /api/auth/register → bcrypt 哈希 → 落库 → 返回 JWT
登录: POST /api/auth/login → 校验哈希 → 签发 JWT（含 user_id、过期时间）
鉴权: 请求带 Bearer → get_current_user 依赖校验 → 注入当前用户
```

## 8. 安全设计

- 密码：`bcrypt`（passlib），不存明文。
- JWT：access token 有效期 24h，`HS256`，secret 来自环境变量。
- 分享 token：`secrets.token_urlsafe(32)`，随机不可枚举；可选过期时间。
- 行程隔离：所有行程接口强制 `user_id` 过滤，防止越权访问（IDOR）。
- CORS：白名单（仅前端域名）。
- 输入校验：Pydantic 全量校验；SQL 注入由 ORM 参数化防护。
- 敏感信息：API key 一律走环境变量（`.env`，不入库、不进仓库）。

## 9. 部署方案（小规模上线）

`docker-compose.yml` 三服务：

```
┌─ nginx ──────┐   :80 静态前端 + /api 反代到 backend:8000
├─ backend ────┤   uvicorn app.main:app（含 Node.js + MCP 服务器）
└─ postgres ───┘   postgres:16，数据卷持久化
```

- 前端 `npm run build` 产物由 Nginx 托管，`/api`、`/s` 反代后端。
- 环境变量：`.env`（后端）、构建期注入 `VITE_*`（前端）。
- **高德 MCP**：后端容器需内置 Node.js（`npx` 拉起 `@amap/amap-maps-mcp-server`，Dockerfile 已安装并全局预装），运行期需出网访问高德 REST API。
- 日志：loguru 输出结构化日志，容器日志采集。
- 健康检查：Nginx 探活 `/health`。
- 备份：PostgreSQL 定时 `pg_dump`（可选）。

> MVP 阶段用同步请求 + 前端 loading（超时 3 分钟，实测生成约 35s）；若生成耗时增长或并发上升，再引入任务队列（Celery + Redis 或 arq）+ 进度轮询 / SSE，架构已预留演进点。

## 12. 相对第一版的改进总结

1. **地图接入更稳**：从托管 SSE MCP 端点改为本地 stdio 子进程（官方 `@amap/amap-maps-mcp-server`），消除长连接被断开（`ClosedResourceError`）的问题。
2. **工具调用结构化**：`langchain-mcp-adapters` 确定性调用官方 MCP 工具，替代手写 `[TOOL_CALL:...]` 文本格式。
3. **新增路线规划**：`enrich` 节点对每日相邻景点调用 `direction_*`，生成步行/驾车/公交路线（里程 + 耗时 + 步骤）。
4. **坐标回填修复**：`search_detail` 补齐 + 名称回填 + `maps_geo` 兜底，地图标记正常显示（实测 0 缺失）。
5. **输出可靠**：LLM JSON 模式 + `TripPlan.model_validate()` 校验，替代字符串截取 JSON；目标 schema 剔除 `routes`，路线由确定性节点补。
6. **天气按天**：`maps_weather` 一步到位，无需先查 adcode。
7. **持久化与账户**：同步 SQLAlchemy + JWT + 用户系统，行程从 `sessionStorage` 升级为服务端历史。
8. **分享能力**：token 只读分享 + 过期时间。
9. **前端工程化**：Pinia、Axios 拦截器、环境变量化；新增路线渲染与每日折线。
10. **可部署**：Docker + Nginx + Compose，后端镜像内置 Node.js 以运行 MCP 子进程。
